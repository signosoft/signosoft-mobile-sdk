[x] The handwritten (biometric) field cannot be signed. DIAGNOSED 2026-08-17.
    Constraint (Petr): "We want both simple and biometric ... I actually managed
    to ONCE sign both fields in the SDK, so its possible somehow."

    CAUSE. The WASM signpad driver is gated by an origin allowlist carried inside
    the signpad licence. `https://www.signosoft.com` is not on that list, so the
    driver refuses to initialise and the pad renders "Connection error.".
    The list is returned in plaintext by one unauthenticated call:

        curl -s -X POST https://api-test.signosoft.com/v1/public/driver-leases/create \
          -H 'Content-Type: application/json' \
          -d '{"token":"019e6f06-2504-747e-a6da-1d7281a9ff7b","validityHours":24}'

    licenceData.origin, as of 2026-08-17:
        http://127.0.0.1:3000        http://localhost/
        http://localhost:4200        http://localhost:4204
        http://localhost:8000        https://apps.signosoft.com
        https://apps-test.signosoft.com
        https://apps-sandbox.signosoft.com
        https://demo.signosoft.id    capacitor://localhost

    PROOF. Same bioid, same field, same JS DRIVER badge, only the origin differs:
      www.signosoft.com/mobilesdk  -> "Connection error.", Confirm disabled
      apps-test.signosoft.com      -> live pad, "Please sign using your mouse.",
                                      ink renders, Confirm Signature enables
    Reproduces in a plain desktop browser, so it is not the SDK, the simulator or
    WKWebView.

    CONFLICT, unresolved: an allowlisted origin would explain Petr signing the
    pad field once, but the 2026-08-18 e2e test found that one bioid authorises
    only ONE signature regardless of origin (see the next section), which would
    make signing BOTH fields impossible either way. One of the two findings is
    incomplete. Do not present either as settled until this is resolved.

    NOT the cause, ruled out: the signpadLeaseToken is alive and minted a valid
    licence on 2026-08-17. An expired lease was the previous theory and it is
    wrong.

    NOT PROVEN: that a biometric signature completes and stamps. The pad accepts
    input and enables Confirm; confirming would consume the bioid and was not
    done. Someone should complete one on an allowlisted origin.

    TWO WAYS TO FIX, neither inside this repository:
      A. Add https://www.signosoft.com to the lease's origin allowlist,
         server-side, by whoever owns the licence service. The SDK needs no
         change at all. Recommended.
      B. Deploy the embedded shell to an already-allowlisted origin and point
         baseUrl at it. baseUrl is already a parameter of open(), so this is also
         a zero-code change on our side. Note apps-test.signosoft.com currently
         serves the full app, not the embedded build.


FOUND BY THE E2E TEST, 2026-08-18
--------------------------------------------------------------------------------

Full write-up with screenshots and server-state read-back:
docs/E2E-TEST-2026-08-18.md. Tested on the iPad Pro 13" and iPhone 17
simulators. Nothing below is an SDK defect — the SDK behaved correctly in every
run.

[ ] One bioid authorises exactly ONE signature, so the demo document can never
    complete. The demo mints two fields. Whichever is signed first succeeds; all
    remaining fields are then permanently unsignable with that token, including
    after closing and reopening the ceremony. Shown three times, with server
    state read back from openDocLink each time:
        331012  2x simple, signed left  -> right refused
        331013  2x simple, signed right -> left refused, and again after reopen
        331014  1x simple               -> finalised, Signed delivered
    Consequence: a client following the demo never receives a terminal result.
    NOTE: this contradicts Petr's recollection of signing both fields once, so
    confirm before treating it as settled.
    Cheapest demo fix: mint a one-field document. Proven to reach Signed with the
    signed PDF returned across the bridge.

[ ] Decide whether one-signature-per-bioid is intended. If one signer is meant to
    fill several fields in a document, either the backend mints a token per
    signature or this is a defect. Product/backend question, not ours.

[ ] `Cancelled` can arrive after server state has already changed. Signing the
    typed field and then closing with X reports Cancelled to the host, but that
    signature is recorded server-side (sigsigned=true). docs/INTEGRATION.md tells
    integrators Cancelled means state is unchanged. Pre-existing close-button
    behaviour, a different path from the teardown case commented in
    SignosoftSignerViewController.viewDidDisappear.

[ ] No way to finish a partly-signed document from inside the ceremony. The doc
    menu has Rename, Attachment, Send to email, Validate, Audit Trail, Download,
    Search, Thumbnails, Print — no Finalize. Tenant reports
    allowPartialFinalize: false, so the only exit is cancelling.

[ ] tools/mint-bioid.mjs:113 passes the field index as the auth-method order:
        sigauthmethods: [{ type: f.authmethod, order: i }]
    `order` is the position within one signature's own auth-method list, so a
    single method should be 0, not the field index. Looks wrong and worth fixing.
    IT IS NOT THE CAUSE OF ANYTHING OBSERVED: rebuilding with order: 0 on both
    fields changed nothing, the second field still refused. Do not re-blame it.

ROBUSTNESS BUGS — NOT SECURITY
--------------------------------------------------------------------------------

All recorded in full in docs/SDK-HARDENING-CHANGES.md with reasons and a diff.
Petr: security "is for now out ... there is no real need for security yet to be
honest". These five are about the SDK working rather than about it being
attacked, so they outlive that decision.

#9 and #14 are SCHEDULED — wave 3, agent `signer-fix`. Petr approved them
2026-08-17 on the grounds that they are contract bugs rather than security: the
docs, as rewritten in wave 2, now promise a client both behaviours in writing.
The alternative considered and rejected was weakening the prose instead.

[>] #9  A signer torn down without a result never completes. The Dart Future
        hangs forever and `isPresenting` in SignosoftSignerPlugin.swift:15 stays
        true, so every later open() returns alreadyOpen for the app's lifetime.
        NOT reachable in the medicly demo: presentation is .fullScreen, which
        has no swipe-to-dismiss. Reachable in a client app that navigates away
        mid-ceremony — which is exactly what a client will build.

[ ] #10 SignedInfo is built on the main thread, base64-decoding up to 32 MB and
        writing it to disk inline. Invisible at the demo's 204 KB; a visible
        freeze at the ceiling.

[ ] #11 An empty documentToken is reported as a successful signature. The host
        then calls its backend with nothing.

[ ] #13 finish() reports but does not stop the page, so a ceremony holding a
        camera stream keeps running if the host forgets to dismiss.

[>] #14 Dart open() is documented "Never throws" and does — only
        PlatformException and MissingPluginException are caught, so a codec
        error or a malformed reply escapes into the caller's await. README.md
        states the guarantee outright, which makes this a written promise the
        code does not keep. Separately, onDiagnostic is invoked unguarded inside
        an async handler, so a host callback that throws surfaces as an
        unhandled async error attributed to the SDK.


STANDING
--------------------------------------------------------------------------------

- No CLAUDE.md in this repository. Every other project's prompt template starts
  with "read CLAUDE.md"; here there is nothing to read. House rules, the gates,
  how to run the demo, and the invariants all live in people's heads.

- Never run `flutter clean` in examples/medicly or signosoft_signer/example.
  Their build/ entries are symlinks out to ~/.flutter-build; codesign rejects
  frameworks built under an iCloud-synced directory. Deleting the symlink fails
  the Xcode build with status 255 and no useful error.

- Uninstall the app between simulator runs. Stale WebKit cache survives a
  reinstall and makes the shell resolve an empty docLink, which the server
  reports as DOC_LINK_NOT_EXIST on a perfectly valid token.

- Never pass BIOID as an env-var prefix — `BIOID=abc flutter run
  --dart-define=BIOID=$BIOID` silently passes an empty token. Use command
  substitution inside the flag.

- The test tenant returns showPRReject: false, so the Rejected outcome still
  cannot be exercised end to end. Server-side tenant configuration.
